# MCSaveHelper 日志系统架构设计

> 状态：阶段 1 已确认，采用方案 A（纯文本 JSONL）。后续实现以本文为基线。
>
> 适用范围：`app/qtui`、`app/controllers`、`app/services`、`core` 和进程入口。本文定义架构与
> 边界，不替代各阶段的 API 文档、UI 交互设计和测试。

## 1. 目标和现状

MCSaveHelper 是单进程 PySide6/Qt6 桌面应用，日志系统必须只使用 Python 标准库和现有 PySide6，
并提供统一记录、异步本地落盘、查看筛选、统计、异常聚合和告警能力。日志不得记录凭据、完整
NBT 数据或无必要的用户隐私。

仓库已有可复用实现：

- `core/logger.py` 提供兼容门面，业务代码使用 `logger.info(..., module="Backup")`。
- `core/logging/manager.py` 通过后台 worker 和队列分发。
- `core/logging/handlers.py` 已有控制台、按大小轮转文件和 UI handler。
- `core/logging/models.py` 已有时间、级别、模块、线程和 `extra` 字段。
- `app/qtui/log_panel.py` 已有底部可停靠日志面板和 Qt 主线程投递保护。
- `app/qtui/application.py` 已接入启动、UI handler 安装和窗口关闭移除。

本次改造保留这些导入路径和 handler 契约，内部接入标准库 `logging`，再增加 JSONL 存储、查询
服务和模型视图。SQLite 不作为方案 A 的运行时依赖。

## 2. 数据流

```text
业务模块 / 标准 logging / 可选 stdout-stderr 兼容流
                     |
                     v
              core.logger 兼容门面
                     |
            logging.Logger + 入队 handler
                     |
              有界异步队列（worker）
                     |
                     v
        DailyJsonlHandler（单写线程）
          |             |              |
          v             v              v
     按天 JSONL     emergency 文件    Console/UI handler
          |
          +--> LogQueryService（后台流式扫描）
          |          |
          |          +--> LogStatsService / 异常聚合
          |          +--> AlertService / 通知端口
          |
          +--> LogViewerController --> QAbstractTableModel/QTableView
```

不变量：调用线程只构造记录和快速入队；JSONL、查询、导出、统计、邮件和 Qt 控件都不在调用
线程执行。实时 UI 事件在一条 JSONL 成功追加后发布；归档写失败不会伪装成成功，会切换到
emergency 文件并在 UI 显示存储降级。

## 3. 存储方案对比

### 3.1 方案 A：纯文本文件（已选择）

记录以 UTF-8 JSON Lines 保存于日志目录：

```text
~/.mc_save_helper/logs/
  current/app-2026-08-17.jsonl
  archive/app-2026-08-16.jsonl
  emergency/emergency-2026-08-17.log
```

每天生成独立文件；同一天超过大小上限时增加 `.1`、`.2` 分片。查询服务按时间筛选先定位
日期文件，再后台逐行解析；模块、级别和关键词条件在解析后过滤。近期日志维护小型内存索引
（文件名、字节偏移、时间桶），只用于减少扫描范围，不作为持久化事实源，应用重启后可重建。

优点：零数据库迁移、文件可直接排障和复制、单文件损坏隔离、顺序追加简单可靠。缺点：复杂
筛选和统计需要扫描，数据量大时比 SQLite 慢；查询必须后台执行并限制时间范围；异常聚合和告警
不能依赖数据库 `GROUP BY`，由流式聚合完成。

### 3.2 方案 B：SQLite 数据库

所有日志进入 SQLite，以时间、级别、模块和指纹索引查询。多条件筛选、统计和滑动窗口告警
性能最好，但引入 schema 迁移、数据库损坏恢复、checkpoint、备份和单库故障点。该方案不采用。

### 3.3 方案 C：SQLite + 文本归档

近期日志进入 SQLite，历史归档为 JSONL。它兼顾查询和人工排障，但存在双写一致性、保留窗口和
恢复语义的额外复杂度。用户已明确选择方案 A，因此不实现双写。

## 4. 方案 A 的容量与轮转策略

| 项目 | 默认值 | 行为 |
|---|---:|---|
| 单日主文件大小 | 25 MB | 写入前检查，达到上限切换同日序号分片 |
| 单条记录上限 | 1 MB | 消息、堆栈和 `extra` 超限时截断并记录原长度 |
| 普通归档保留 | 90 天 | 只删除日志系统目录内、按日期确认的文件 |
| 总目录软上限 | 500 MB | 先删除最旧完整日期；失败则提示用户 |
| 查看器默认范围 | 最近 1 天 | 用户扩大范围时仍在后台线程扫描 |
| 查看器加载上限 | 300 条 | 保留最新匹配记录，不把全部结果装入内存 |
| 异步队列 | 20,000 条 | 低级别可丢弃；高级别短暂等待并报告队列压力 |

文件名由受控日期和序号生成；清理前使用 `Path.resolve()` 验证路径位于日志根目录，不跟随符号
链接或 junction。启动、运行期轮转和达到总容量时都会执行保留策略；这些操作只发生在日志
worker 或维护任务，不阻塞 Qt 主线程。

## 5. 日志记录格式

### 5.1 规范字段

每行是一个完整 JSON 对象，`schema_version` 固定为 1；未知字段读取时忽略，写入时不覆盖规范
字段。

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | integer | JSONL 格式版本 |
| `timestamp` | string | 带时区 ISO 8601 显示时间 |
| `timestamp_utc_us` | integer | UTC Unix 微秒，用于确定排序/筛选 |
| `level` | string | DEBUG/INFO/WARNING/ERROR/CRITICAL 或扩展级别 |
| `category` | string | UI 五级分类 DEBUG/INFO/WARN/ERROR/FATAL |
| `module` | string | 稳定业务来源，如 `Backup`、`QtApp` |
| `logger_name` | string | 标准库 logger 名称 |
| `process_id` | integer | 进程 ID |
| `thread_id` | integer | 线程 ID |
| `thread_name` | string | 线程名 |
| `message` | string | 已格式化的主消息 |
| `exception_type` | string/null | 异常类型名称 |
| `exception_message` | string/null | 异常消息 |
| `stack_trace` | string/null | 完整格式化堆栈 |
| `extra` | object | 可选结构化字段，键值 JSON 可序列化 |
| `fingerprint` | string/null | ERROR/FATAL 异常聚合指纹 |
| `created_at_utc_us` | integer | 入队到持久化前的诊断时间 |

示例：

```json
{"schema_version":1,"timestamp":"2026-08-17T03:12:45.123456+08:00","timestamp_utc_us":1786907565123456,"level":"ERROR","category":"ERROR","module":"Backup","logger_name":"app.services.backup_service","process_id":18420,"thread_id":9024,"thread_name":"BackupWorker","message":"创建备份失败","exception_type":"OSError","exception_message":"磁盘空间不足","stack_trace":"Traceback ...","extra":{"backup_size_bytes":134217728},"fingerprint":"sha256:...","created_at_utc_us":1786907565124000}
```

`extra` 保持嵌套，避免键名覆盖规范字段。包含 `password`、`token`、`secret`、`authorization`、
`cookie` 的键默认脱敏；绝对路径和存档标识按导出设置隐藏用户目录前缀。

### 5.2 级别兼容

对外规范级别为 DEBUG、INFO、WARN、ERROR、FATAL；标准库名称 WARNING/CRITICAL 分别显示为
WARN/FATAL。现有 SUCCESS（25）和 API（15）继续支持，详细记录保留原名，统计时归入 INFO。

### 5.3 异常指纹

ERROR/FATAL 且含异常时，使用异常类型、归一化消息和前 3 个应用栈帧的模块/函数名计算 SHA-256。
文件绝对路径、行号、十六进制地址和明显变化的数字不参与指纹。没有异常对象的 ERROR 使用
`module + 归一化 message` 作为弱指纹。原始消息和堆栈始终保留，指纹只用于流式聚合。

## 6. 组件和依赖边界

```text
core/logging/
  facade / stdlib bridge / record normalization / queue
  daily JSONL writer / rotation / retention / fingerprint
       ^
       |
app/services/
  log_query_service / log_stats_service / log_export_service / alert_service
       ^
       |
app/controllers/
  log_viewer_controller / alert_controller
       ^
       |
app/qtui/
  log viewer widgets / QAbstractTableModel / notification adapter
```

- `core/logging` 只依赖标准库，不能导入 `app` 或 PySide6。
- `app/services` 编排流式查询、统计、导出和告警，依赖抽象的日志存储端口。
- controller 持有筛选条件、查询 generation、实时模式和告警调度，不持有 Qt 控件。
- `app/qtui` 负责控件、`tr()`、信号槽、QSettings、系统托盘和剪贴板。
- 应用级服务通过 `AppServices`/`ServiceFactories` 显式装配；日志 manager 是允许共享生命周期的
  进程级基础设施，但必须显式初始化、刷新和关闭。

## 7. 异步写入、过载和关闭

阶段 2 使用标准库 `logging.Logger` 和兼容入队 handler；阶段 7.1 的 `DailyJsonlHandler` 由唯一
worker 写入。队列满时 DEBUG/INFO 可丢弃，WARN 短暂等待，ERROR/FATAL 最多等待 50 ms，仍失败
则追加 `emergency-YYYY-MM-DD.log`。丢弃数量按级别累计，队列恢复后写一条合并诊断，诊断本身
不得再次进入同一 logger。

关闭顺序：

```text
停止实时订阅 -> 停止告警调度 -> 记录退出消息
-> 排空队列 -> flush JSONL 并关闭句柄 -> 移除 stdlib bridge -> 关闭 Qt
```

`shutdown()` 幂等并有有限超时；超时会把未刷新数量写入 emergency 文件。所有文件句柄在成功、
失败和取消路径释放。

## 8. 查询、统计、聚合和告警

### 8.1 流式查询

查询条件包含级别集合、UTC 起止时间、关键词、模块、排序方向和页游标。查询器先按日期列出
文件，再逐行 `json.loads`；损坏行跳过并返回“损坏行数量”诊断，不使整日查询失败。页游标由
`(文件日期、文件序号、字节偏移)`组成，结果以 dataclass 返回。大范围扫描经
`ExecutionRuntime` 或 QRunnable 后台执行，generation 变化时取消或丢弃结果。

### 8.2 统计和异常聚合

今日日志总量、五级占比和近 7 天趋势均通过后台流式扫描计算，返回覆盖范围和生成时间。异常
聚合使用字典按 fingerprint 统计次数、首次/最近时间、代表消息和实例位置；只保留摘要，点击
后再加载实例堆栈。可选内存日期索引只是加速器，重启后由文件重建。

### 8.3 告警

规则包含名称、启用、级别、窗口分钟数、阈值、通知方式、冷却分钟数和邮件收件人。默认每 5
分钟后台扫描规则窗口；相同规则处于冷却期时不重复通知，但记录抑制次数。系统通知优先使用
`QSystemTrayIcon.showMessage()`，不可用时回退非阻塞 UI 提示。邮件使用标准库 `smtplib` 和
`email.message`；SMTP 密码不写入日志，QSettings 只保存非秘密配置，密码使用会话值或环境变量。

## 9. Qt 查看器约束

阶段 3 将比较独立窗口、底部停靠和侧边标签三种布局；当前固定以下约束：

- 延续底部可停靠 `QDockWidget` 集成点，避免新增顶层导航页面。
- 列表使用 `QTableView + QAbstractTableModel`，后台按页追加，禁止用 `QTextEdit` 承载历史全量。
- 筛选栏提供 All/Debug/Info/Warn/Error/Fatal、时间范围、关键词和模块筛选。
- 详情面板按 ID/文件位置加载完整消息和堆栈；实时模式只在持久化成功事件后追加。
- 实时关闭时显示“有 N 条新日志”按钮；开启时批量追加并滚动到底部。
- 清空、导出、复制、空状态、加载中、无匹配和存储已满状态都通过稳定占位反馈。
- 列宽、筛选条件、dock 状态、详情区比例和实时开关使用 `QSettings` 持久化。
- 所有可见文本同时加入 `translations/zh_CN.json` 和 `translations/en_US.json`，并通过 `tr()`/翻译端口
  获取；后台线程不得直接操作 Qt 控件。

## 10. 生命周期和兼容迁移

日志初始化应早于应用服务装配，默认目录为 `~/.mc_save_helper/logs`。打包态启动失败继续写
可执行文件同目录 `startup_error.log`，日志初始化后再追加结构化启动诊断。

兼容调用保持：

```python
from core.logger import logger

logger.info("创建备份", module="Backup")
logger.info("创建备份", module="Backup", extra={"size_bytes": 134217728})
logger.error("创建失败", module="Backup", exc_info=True)
logger.fatal("无法继续", module="Core", exc_info=True)
```

标准库 `logging.getLogger(__name__)` 通过 root bridge 进入同一队列，记录保留 logger 名称和参数化
消息。可选 stdout/stderr 重定向必须显式启用、可恢复，并让 ConsoleHandler 写 `sys.__stdout__` /
`sys.__stderr__`，防止 print 与日志递归；启动错误路径不依赖重定向。

## 11. 分阶段实施与验收

1. **阶段 2**：标准库 logging 桥接、统一门面、结构化 `extra`、`exc_info`、`warn`/`fatal` 和 API 文档。
2. **阶段 7.1**：`DailyJsonlHandler`、按天/大小轮转、保留/容量、emergency 降级和流式查询端口。
3. **阶段 3-4**：Qt 模型视图、布局方案确认、筛选、详情、实时状态和导出。
4. **阶段 5**：统计、趋势、异常聚合、规则 CRUD、系统/邮件通知和告警历史。
5. **阶段 6**：组合根生命周期、标准 logging 全局接入和可选 print 兼容。
6. **阶段 8**：相关测试、完整 `pytest -q`、flake8/mypy/pyright/compileall/diff 检查和启动验证。

测试必须覆盖损坏 JSON 行、跨日轮转、文件满、路径越界、并发查询、队列过载、异常指纹、告警
冷却、重启索引重建和窗口关闭刷新；测试数据使用 `tmp_path` 或仓库内可访问临时目录，不修改
真实存档或用户配置。
